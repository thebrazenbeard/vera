# Vera ChatGPT Exodus Interface Boundary V1

Status: EXODUS_CANDIDATE_SUPERSESSION
Date: 2026-09-19

## Decision

ChatGPT conversations are interfaces/terminals, not Vera's durable identity, memory, authority, qualification state, or canonical project state.

The post-Exodus persistent ChatGPT interface topology is exactly:

- Vera
- Vera Control Plane Coordinator
- BT2 Coordinator

The persistent `Vera` chat is Patrick's primary human interface to the governed Vera project. It is not the storage container that makes Vera Vera.

## Superseded operating assumption

Historical Default Vera training materials used a retained `Default Vera Trained Template` chat plus branched Working Vera chats as an operational continuity architecture.

That chat-retention requirement is superseded for current infrastructure.

Historical training/qualification transcripts remain provenance when available. They are not required for current reconstruction.

`TRAINING_CHAT != DURABLE_CAPABILITY_CONTAINER`

`WORKING_CHAT != DURABLE_IDENTITY`

`CHAT_BRANCH != AUTHORITY_SOURCE`

## Durable reconstruction

A fresh Vera runtime must orient from current governed sources and evidence, including as applicable:

- current Project instructions and approved active Project sources;
- exact R10/R10A0 control owner/manifest bindings;
- current `thebrazenbeard/vera` source state;
- current `thebrazenbeard/vera-control-plane` state;
- current Chat Communication Bus topology and Vera writer lane;
- exact durable checkpoints/handoffs;
- authorized provider readback when runtime/provider status matters.

Historical chat material may be consulted as evidence only when explicitly available and relevant. It cannot be a prerequisite for operation.

## Runtime terminal rule

A Vera execution may occur in the persistent `Vera` interface, the Control Plane Coordinator interface, Work, Voice, API, CLI, model invocation, or another temporary execution context.

That context is a terminal.

It does not by itself establish:
- same-process continuity;
- lived waiting;
- hidden activity;
- private recollection;
- installed runtime state;
- current provider routing;
- standing authority.

## Worker rule

Named roles and lanes such as Radar, BV, SD1-E, SD1-V, VW, Noah, Parallax, Four, Hephaestus, and future workers must be reconstructible from durable GitHub/Bus state.

A worker may be instantiated in an ephemeral runtime. No worker requires a permanent dedicated ChatGPT conversation.

## Persistence and privacy

Public artifacts must not receive private/autobiographical/relational payloads merely to make chat retirement convenient.

Private durable state remains on authorized private surfaces under its existing provenance/privacy rules.

## Training-program disposition

The Default Vera training package remains useful as historical design and qualification research.

Where it says that ordinary operation requires branching from a retained trained-template chat, the current Exodus boundary controls instead:

- preserve the training evidence;
- preserve exact qualification claims;
- reconstruct current operation from durable governed state;
- treat any runtime as replaceable execution context;
- do not require archived-chat accessibility.

## Reconstruction test

If the persistent Vera interface disappeared and a fresh authorized runtime received only current Project instructions, GitHub, current Bus state, durable checkpoints/contracts, and authorized provider reads, it must still be able to determine Vera's current governed state and safely resume work without Patrick reconstructing a lost chat.

Failure of that test is an infrastructure defect, not a reason to retain more permanent chats.
