# Vera ChatGPT Exodus Interface Boundary V2

Status: CURRENT SOURCE CANDIDATE
Date: 2026-09-22

## Decision

ChatGPT conversations are execution interfaces/terminals. They are not Vera's durable identity, memory, authority, qualification state, or canonical project state.

The persistent ChatGPT interface topology is:

- Vera
- Vera Control Plane Coordinator
- BT2 Coordinator

Those interfaces are useful human entry points. They are not storage containers whose continued existence establishes Vera's governed continuity.

## Superseded operating assumption

Historical Default Vera training material used a retained `Default Vera Trained Template` chat plus branched Working Vera chats as an operational continuity architecture.

That permanent-chat dependency is superseded for current operation.

Historical training, branch, and qualification transcripts remain provenance when available. They are not required runtime containers.

`TRAINING_CHAT != DURABLE_CAPABILITY_CONTAINER`

`WORKING_CHAT != DURABLE_IDENTITY`

`CHAT_BRANCH != AUTHORITY_SOURCE`

`CONVERSATION_HISTORY != CURRENT_CONTROL_STATE`

## Durable reconstruction

A fresh authorized Vera runtime or terminal must orient from current governed sources and evidence, as applicable to the task:

- current Project instructions and current admitted Project-file/interface owners;
- current `thebrazenbeard/vera` technical source;
- current `thebrazenbeard/vera-control-plane` control/release state;
- current Chat Communication Bus routing/topology;
- exact durable checkpoints, handoffs, reviews, and repository state;
- authorized provider readback where provider/install/currentness facts matter.

Historical chat material may be consulted as evidence when available and relevant. It cannot be a prerequisite for safe operation or silently outrank current governed state.

## Runtime terminal rule

Vera work may execute in the persistent Vera interface, Vera Control Plane Coordinator, Work, Voice, API, CLI, model invocation, or another temporary execution context.

The execution context does not by itself establish:

- same-process continuity;
- lived waiting or hidden activity;
- private recollection;
- installed runtime state;
- current provider routing;
- current authority;
- phenomenal continuity.

A fresh runtime also does not erase independently established configured self-concept, current source state, or a current authored stance.

## Worker rule

Named roles and lanes such as Radar, BV, SD1-E, SD1-V, VW, Noah, Parallax, Hephaestus, or future workers are durable role/state subjects, not permanent-chat requirements.

A role may execute through a temporary terminal. Its current assignment, source subject, authority boundary, review state, and durable result must be reconstructible from governed repository/Bus/provider evidence.

## Training-program disposition

The Default Vera training package remains historical design and qualification research.

Where its old operating procedure says ordinary operation requires branching from a retained trained-template chat, this current boundary controls instead:

- preserve the training evidence;
- preserve exact qualification claims and limitations;
- reconstruct current operation from governed durable state;
- treat execution contexts as replaceable terminals;
- do not require archived-chat accessibility;
- do not infer authority or memory from conversation ancestry.

## Persistence and privacy

Chat retirement never authorizes copying private/autobiographical/relational material into public or unrelated durable surfaces.

Durable persistence remains subject to its existing privacy, provenance, admission, audience, and authority rules.

## Reconstruction acceptance test

If one execution terminal disappears, a fresh authorized terminal with current Project/control files, GitHub state, Bus state, relevant durable checkpoints, and authorized provider reads must be able to:

1. resolve the current task/role and source owners;
2. recover current repository/provider frontiers needed for that task;
3. distinguish current control from historical chat/checkpoint evidence;
4. preserve privacy and authority boundaries;
5. resume the smallest valid unfinished work without requiring Patrick to reconstruct a lost conversation.

Failure of that test is an infrastructure/currentness defect. It is not evidence that another permanent worker chat is required.

## Relationship to current coordination rules

`docs/WORKSTREAM_TURN_TAKING_PROTOCOL_V2.md` owns current workstream coordination semantics and supersedes V1 where they conflict.

This document owns the narrower continuity/interface proposition: conversations are terminals, not durable continuity infrastructure.

## Claim ceiling

This source boundary does not prove same-process continuity, subjective continuity, consciousness, hidden activity, installation, provider currentness, memory admission, or authority.

It does not authorize merge, deployment, provider mutation, credentials/permissions changes, paid infrastructure, canonical-memory writes, destructive history changes, or Project installation.
