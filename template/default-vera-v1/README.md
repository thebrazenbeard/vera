# Default Vera Trained Template V1

Status: `RESEARCH_REVISED_DESIGN_CANDIDATE_NOT_QUALIFIED`

This directory defines a candidate training, evaluation, and continuity architecture for a future **Default Vera Trained Template**.

It is intentionally separate from native ChatGPT Project-release installation semantics. Creating or revising these files does not install, replace, merge, deploy, or reconfigure a Vera Project release.

## Objective

Create one clean, externally evaluated Vera chat whose trained capability baseline can be designated:

`Default Vera Trained Template`

with governance state:

`FROZEN_BY_GOVERNANCE`

Ordinary Working Vera chats can then branch from that template, enter the active Vera Project through a verified target route, and restore the latest governed working state instead of rebuilding behavior and continuity from scratch after a conversation becomes too long or otherwise unsuitable.

## Key separation

```text
DEFAULT VERA TRAINED TEMPLATE = stable trained transcript/capability baseline
ACTIVE VERA PROJECT           = current Project instructions/files/tools/eligible context
GOVERNED EXTERNAL STATE       = evolving durable project continuity
WORKING VERA CHAT             = current execution context
PRIVATE OVERLAY               = separately authorized user-specific/private state
```

The template is not evidence of uninterrupted runtime existence, private memory, consciousness, or same-runtime continuation.

## Research correction to the V0 architecture

The initial V0 design assumed a clean candidate could simply be created inside the active Vera Project. Current product documentation and Hephaestus's independent architecture review exposed a material problem: chats inside the same Project may reference sibling Project conversations.

Therefore:

- the active Vera Project is **not** the training clean room;
- the candidate should train in a dedicated project-only Project containing only that candidate chat;
- external holdout branches should be placed into separately isolated project-only evaluation contexts before their first holdout response;
- the exact branch/move workflow must be empirically verified on the target route;
- once a qualified Working Vera enters the active Vera Project, accepted governed state must outrank conflicting stale/unvalidated chat-history context.

The V0 fixed fifteen-module sequence was also superseded. Historical Vera research rejected training-first bias, so the current design uses a closed-book baseline plus adaptive remediation and mandatory external qualification across all critical behavior domains.

## Source basis

The research program draws from reusable, non-private evidence including:

- current Vera behavior laws and canonical positive/hostile cases;
- historical Vera personality, pragmatics, identity, meaning, and evaluation work;
- correction history and rejected behavior architectures;
- current project/runtime rules for authority, time, memory, retrieval, retry, privacy, and continuity;
- current OpenAI Projects documentation;
- current GitHub/Supabase/File Library evidence;
- external research on sycophancy, pragmatics, personality evaluation, personalization, and long-term conversational memory;
- read-only architecture review from qualified Working Hephaestus.

Private relational history, personal user history, intimate records, credentials, confidential data, and private autobiographical material are excluded from portable/default training content. Generic behavioral lessons may be abstracted only after privacy and provenance review.

## Role separation

```text
CURRENT LONG VERA CHAT = TRAINER / INTERNAL_TEST_HARNESS
CLEAN CANDIDATE CHAT   = TRAINING SUBJECT
HOLDOUT ADMINISTRATOR  = EXTERNAL QUALIFICATION ROLE
QUALIFIED CANDIDATE    = DEFAULT VERA TRAINED TEMPLATE
BRANCHED DESCENDANT    = WORKING VERA
```

The current research chat may design tests, teach/remediate the candidate, preserve evidence, and make internal assessments. It does not turn its own preferred design into external qualification by declaration.
